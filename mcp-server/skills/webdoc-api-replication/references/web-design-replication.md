# 网页设计原则 → 更快复刻

本文件回答：**网页设计上有哪些原则，它们各自对应哪个接口，以及怎么用它们减少工作量。**

**本文件不教人做好看的网页。** 它把设计原则当作**接口发现线索**：
一条设计原则往往意味着「页面某处会消费某类数据」，而那类数据背后一定有接口。

> 引用纪律：本文件的 WCAG 条款文本逐字取自 W3C `https://www.w3.org/TR/WCAG22/`（最终版），
> 设计令牌格式取自 DTCG 稳定版 `2025.10`。其余为本仓推论，**明确标为本仓推论**。

---

## 0. 核心论点：设计原则是接口的索引

复刻网页时，人容易先盯视觉。视觉是最难验证、也最难自动化的一层；
而**页面上的每一块内容都来自某个接口**。所以正确顺序是反过来的：

```
设计原则  →  页面需要什么数据  →  接口要提供什么  →  抓包/扫描找接口
```

举例：

| 设计原则 | 页面因此需要的数据 | 对应接口 |
| --- | --- | --- |
| 分页 / 无限滚动 | 列表 + 总数 + 下一页游标 | 列表接口（带分页参数） |
| 状态提示（`4.1.3`） | 每个操作的结果反馈 | 写接口的响应状态 |
| 错误标识（`3.3.1`） | 哪个字段错、怎么改 | 写接口的 4xx 响应体 |
| 表单自动填充（`3.3.7`） | 上次填过什么 | 草稿/预填接口 |
| 多步流程 | 跨步骤保持的中间态 | 步骤间传参（复合命令 `steps`） |
| 响应式（`1.4.10`） | **同一份数据的不同呈现** | 通常**不新增**接口 |

**最后一行是省时间的关键**：响应式断点变化的是**呈现层**，不是**数据层**。
`1.4.10 Reflow` 要求内容在 320 CSS px 宽下不丢信息、不双向滚动——
这说的是布局怎么折，**不是**「窄屏要调另一个接口」。
不知道这点，很容易把每种视口都当成一次独立接口发现，凭空多出几倍工作量。

## 1. 一致性与一致性优先（复刻的总原则）

### 1.1 WCAG 的「一致帮助」条款给出了可操作的口径

> "If a web page contains any of the following help mechanisms, and those mechanisms are repeated on multiple web pages within a set of web pages, they occur in the same order relative to other page content, unless a change is initiated by the user: Human contact details; Human contact mechanism; Self-help option; A fully automated contact mechanism."
> —— WCAG 2.2, Success Criterion 3.2.6 Consistent Help (Level A)

> "The visual position of a help mechanism is likely to be consistent across pages for the same page variation (e.g., CSS break-point)."
> —— WCAG 2.2, 3.2.6 Understanding（注 2）

**复刻含义**：同一页面集合里，重复出现的元素**顺序与位置一致**。
这直接对应接口层的**统一前缀**：同一个站点里 `List*` 系列动作通常共享同一个网关前缀与同一套分页参数。

> 本仓推论：观察到**一个**列表接口的前缀与分页参数形态，
> 就有理由在同一站点**优先尝试**同前缀的其它动作，而不是对每个域重新扫描。
> 但这是**提高检索效率的启发式，不是端点存在性的证明**——
> 端点档位仍按 `rea-principles.md` 的四档判，未命中的记 `unknown`，不记「不存在」。

### 1.2 一致性也是复刻的验收标准

同一条接口在复刻站里应该产出**同样的数据形状**。
若原站 A 页和 B 页的同名列表接口返回结构不同，说明我方复刻漏了区分逻辑——
**一致性差异是漏复刻的信号**，比「页面长得不一样」更早暴露问题。

## 2. 状态与反馈：最容易漏复刻的一层

### 2.1 状态消息必须能被程序确定

> "In content implemented using markup languages, status messages can be programmatically determined through role or properties such that they can be presented to the user by assistive technologies without receiving focus."
> —— WCAG 2.2, Success Criterion 4.1.3 Status Messages (Level AA)

**复刻含义**：页面会区分「进行中 / 成功 / 失败 / 空」等状态。
每个状态背后都对应**接口返回的某个信号**——状态码、响应体某个字段、或空数组。

**动作**：每个列表接口都要覆盖「有数据」和「空数据」两种情况。
只验过有数据的接口，**空态一定是漏的**。

### 2.2 错误标识：接口错误体就是错误文案来源

> "If an input error is automatically detected, the item that is in error is identified and the error is described to the user in text."
> —— WCAG 2.2, Success Criterion 3.3.1 Error Identification (Level A)

> "If an input error is automatically detected and suggestions for correction are known, then the suggestions are provided to the user, unless it would jeopardize the security or purpose of the content."
> —— WCAG 2.2, Success Criterion 3.3.3 Error Suggestion (Level AA)

> "Information previously entered by or provided to the user that is required to be entered again in the same process is either: auto-populated, or available for the user to select."
> —— WCAG 2.2, Success Criterion 3.3.7 Redundant Entry (Level A)

**复刻含义**：表单类接口的 4xx 响应体里带**字段名 + 错误描述**，
前端把它渲染成表单错误提示。所以：

**接口错误响应 = 错误文案的权威来源**。
复刻站应该用**接口返回的错误**渲染错误态，而不是自己写一套静态文案——
否则接口换了个错误码，文案就对不上了。

这与 2.8（错误响应反推参数名）是同一份数据的两个用途。

### 2.3 状态清单（照着验收）

对每个复刻页面，逐条确认这几种状态**都有接口证据**：

| 状态 | 需要的接口事实 | 常见漏法 |
| --- | --- | --- |
| 加载中 | 请求已发出 | 只录到最终态 |
| 有数据 | 2xx + 真实结构 | — |
| 空 | 2xx + 空集合/空字段 | **最常漏** |
| 失败 | 4xx/5xx + 错误体 | 只记「失败」不记体 |
| 无权限 | 鉴权失败响应 | 与「失败」混为一谈 |

## 3. 信息结构与导航：接口清单的地图

### 3.1 名称/角色/值

> "For all user interface components (including but not limited to: form elements, links and components generated by scripts), the name and role can be programmatically determined; states, properties, and values that can be set by the user can be programmatically set; and notification of changes to these items is available to user agents, including assistive technologies."
> —— WCAG 2.2, Success Criterion 4.1.2 Name, Role, Value (Level A)

**复刻含义**：组件的**名字**（如 `aria-label`、`<label>` 文本）与**角色**是稳定的。
同一个角色（如 `tablist`/`tab`、`listbox`/`option`）在原站重复出现时，
背后通常**是同一类接口**。

**动作**：把页面上的重复结构分组——「所有 `option` 角色的元素」很可能来自同一个列表接口。
这比逐个元素去猜快一个数量级。

### 3.2 信息与关系

1.3.1 Info and Relationships (Level A) 要求视觉上表达的结构在代码里也表达出来。

**复刻含义**：层级（面包屑、目录树、折叠区）对应接口的**嵌套资源**。
`/users/{id}/orders` 这种嵌套路径，是页面层级在 URL 上的直接投影。

**动作**：从**导航结构**倒推接口族，而不是从 URL 列表正向看。
面包屑里出现的层级，通常就是资源的父子关系。

### 3.3 焦点可见与目标尺寸：呈现层，不要去找接口

> "When the keyboard focus indicator is visible, an area of the focus indicator meets all the following: is at least as large as the area of a 2 CSS pixel thick perimeter of the unfocused component or sub-component, and has a contrast ratio of at least 3:1 between the same pixels in the focused and unfocused states."
> —— WCAG 2.2, Success Criterion 2.4.13 Focus Appearance (Level AAA)

> "The size of the target for pointer inputs is at least 24 by 24 CSS pixels, except when:"
> —— WCAG 2.2, Success Criterion 2.5.8 Target Size (Minimum) (Level AA)

例外共五类：`Spacing`（间距足够）、`Equivalent`（另有等价控件）、`Inline`（行内文本）、
`User Agent Control`（由用户代理决定）、`Essential`（该呈现是信息所必需）。

> "The visual presentation of text and images of text has a contrast ratio of at least 4.5:1, except for the following:"
> —— WCAG 2.2, Success Criterion 1.4.3 Contrast (Minimum) (Level AA)

例外三类：`Large Text`（大号文本降至 3:1）、`Incidental`（装饰/不可见/非活动组件等）、
`Logotypes`（标志与品牌名）。

**复刻含义**：这三条是**纯呈现层**约束——焦点环粗细、点击热区大小、文字对比度。
它们**不指向任何接口**。

> 本仓推论：复刻时**不要**为满足 `2.5.8` 去追查「点击区域」的接口——
> 热区是 CSS 的事。为它去找接口是纯粹的浪费。
> 真正要追的是「点击这个热区会触发哪个接口」——那才是数据层。

### 3.4 拖拽

> "All functionality that uses a dragging movement for operation can be achieved by a single pointer without dragging, unless dragging is essential or the functionality is determined by the user agent and not modified by the author."
> —— WCAG 2.2, Success Criterion 2.5.7 Dragging Movements (Level AA)

**复刻含义**：拖拽排序背后通常有一个「更新顺序」的**写接口**。
但如果原站只用拖拽、复刻站可以用按钮完成同样功能，那么**不需要复刻那个写接口**
——条款正是这么要求的。

**动作**：写接口是最后考虑的。先把读接口做全，交互方式可以降级。

## 4. 设计令牌：视觉层的单一事实源

### 4.1 令牌格式（DTCG 2025.10）

Design Tokens Community Group（W3C Community Group）的 **2025.10 Final Community Group Report**
（2025-10-28 发布）由三个模块组成：**Format** / **Color** / **Resolver**。

| 模块 | 规定了什么 |
| --- | --- |
| **Format** | 令牌属性 `$type` / `$value` / `$description`；**groups**（分组）与 **alias**（互相引用）；复合类型（shadow、border、typography 等） |
| **Color** | 颜色令牌必须设 `$type` 为 `color`，`$value` 的 `colorSpace` 为**必填**；支持 sRGB、**Display P3**、**Oklch** 及 CSS Color Module 4 的色彩空间 |
| **Resolver** | 在多个上下文（如「light mode」「dark mode」**color themes**）间使用令牌的方法；alias 解析 |

> "This specification extends the format and describes a method to work with design tokens in multiple contexts (such as “light mode” and “dark mode” color themes)."
> —— DTCG Resolver Module 2025.10（§Abstract）

> "For color tokens, the $type property MUST be set to the string color. The $value property can then be used to specify the details of the color"
> —— DTCG Color Module 2025.10（§4.1 Format）

**状态说明**：该文档是 **Community Group Report**，
**不是 W3C 标准，也不在 W3C 标准轨道上**（"It is not a W3C Standard nor is it on the W3C Standards Track."），
但文档自述 "This specification is considered stable"。
引用它作为「设计系统的事实来源」是合适的；把它说成「W3C 标准」是错的。

### 4.2 复刻含义：令牌是呈现层的「接口」

**设计令牌之于视觉，正如 API 之于数据。**

| | 数据层 | 呈现层 |
| --- | --- | --- |
| 事实来源 | 接口响应 | 令牌文件 / CSS 变量 |
| 复刻方式 | 调接口取真实数据 | 复用或重建令牌 |
| 验证方式 | 结构与真实响应一致 | 令牌值与原站一致 |

**动作**：**视觉色板、间距、字号一律从令牌取，不要从截图取色**。
从截图取色会得到「看起来差不多但数值不对」的结果，且无法验证。
这与本仓「响应字段只写字段名与类型、绝不写样本值」是同一种自律：
**能从事实来源取的，就不要从二手观测里估。**

### 4.3 令牌与接口的交界：主题不新增接口

主题切换（浅色/深色）、品牌变体改变的是令牌，**不是数据**。
所以：**不要为每个主题去找一套接口**。

同理，`1.4.11 Non-text Contrast (Minimum) (Level AA)` 要求 UI 组件与图形对象
与相邻颜色对比度 ≥ 3:1——这是**令牌之间**的约束，不是接口之间的约束。

## 5. 用设计原则反推接口清单（可直接照做）

对每个待复刻页面，按下列清单走一遍：

| # | 看什么 | 推出什么接口 | 典型漏项 |
| --- | --- | --- | --- |
| 1 | 导航/面包屑层级 | 资源族与父子关系 | 只有顶层资源 |
| 2 | 列表/卡片区 | 列表接口 + 分页参数 | 只有详情接口 |
| 3 | 表单区 | 写接口 + 必填参数 | 只看字段不看 4xx |
| 4 | 状态提示区 | 状态码语义 | 空态 / 无权限态 |
| 5 | 重复的同类控件 | **一个**接口支撑多处 | 同类控件各调一个接口（错） |
| 6 | 多步流程 | 步骤间传参链 | 跨步骤上下文丢失 |
| 7 | 移动端/窄屏表现 | **通常无新接口** | 误以为要按断点各找一套 |
| 8 | 主题/深色模式 | **通常无新接口** | 误以为要按主题各找一套 |

第 5 行是「更快」的最大来源：一个列表接口同时喂给 8 个下拉框，
比发现 8 个接口快得多，而且**复刻出来也更一致**。
第 7、8 行是「别做无用功」的两条。

## 6. 设计原则不能替你做的事

诚实的边界：

- **设计原则不证明接口存在。** 它只说明「页面某处需要这类数据」。
  端点档位仍按 `rea-principles.md` 四档判定，缺证据记 `unknown`。
- **设计原则不证明接口的字段。** 字段结构只能来自真实响应样本或权威声明。
- **设计原则不替代抓包。** 它只决定「该重点抓什么、什么可以跳过」。
- **无障碍条款不是复刻目标。** 本仓复刻的是**功能与数据**；
  WCAG 条款在此只用作「界面结构的一致性」和「状态完整性」的检查表，
  不用于判定复刻是否合格。

> 一句话：**设计原则负责告诉你「该找什么」，证据口径负责告诉你「找到了算不算数」。**
> 两者不可互相替代——这正是 `rea-principles.md` 存在的理由。
